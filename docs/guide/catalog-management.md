# Catalog management

This guide describes the **runtime catalog** in MCP Composer: the versioned registry stored in PostgreSQL (or in local files during development), how to provision it, which environment variables apply, and how registry operations surface through MCP. It is written for operators and integrators who need one coherent story from schema to process.

For **Skills** as a single `kind` in that registry (payload shape, progressive disclosure, MCP tools, security, and tenancy), see [Skill management](./skill-management.md). For **Backstage-style YAML** generated by scanning MCP servers (a different use of the word “catalog”), see [Catalog and Tool Tagging](./catalog-and-tool-tagging.md).

---

## Setup and enabling catalog MCP

### How to set up the runtime catalog

Follow these steps in order for a **PostgreSQL** deployment (the usual production path).

1. **Create or choose a database** on your Postgres instance. The catalog tables will live in that database (there is no separate `MCP_CATALOG_DATABASE_URL`; the app uses **`MCP_DATABASE_*`**).
2. **Apply the DDL** as one script so extensions and tables are created in order. From the repo root, a typical invocation is:
   ```bash
   psql "$MCP_DATABASE_URL" -f scripts/sql/catalog_schema.sql
   ```
   Use the same connection you will pass to MCP Composer. The script runs **`CREATE EXTENSION IF NOT EXISTS vector;`** and creates **`catalog_resources`**, **`catalog_resource_metadata`**, and **`catalog_embeddings`**.
3. **Set catalog storage environment variables** in the process environment (or a **`.env`** file loaded before start—`catalog_factory` uses `python-dotenv`). At minimum for Postgres:
   - **`MCP_DATABASE_TYPE=postgres`** (must be exactly `postgres`, not `postgresql`).
   - Either **`MCP_DATABASE_URL`** **or** all of **`MCP_DATABASE_HOST`**, **`MCP_DATABASE_NAME`**, **`MCP_DATABASE_USER`**, **`MCP_DATABASE_PASSWORD`**, and optionally **`MCP_DATABASE_PORT`** (default `5432`).
4. **Start a process that uses the catalog** (for example **Catalog Composer**—see below). On startup the catalog adapter opens a pool against the database you configured; no extra in-app migration step runs beyond the SQL you already applied.
5. **Confirm in your DB client** that the three **`catalog_*`** tables exist under your schema (usually `public`).

**Local file mode (development only):** set **`MCP_USE_LOCAL_FILE_STORAGE=true`** and optionally **`MCP_CATALOG_FILE_PATH`** (default directory name **`catalog`**). No **`catalog_*`** tables are used; data lives as files under that root. Do not use this as a shared production registry.

### How to enable catalog MCP with environment variables

The three catalog tool surfaces (**`skill-catalog`**, **`agent-catalog`**, **`workflow-catalog`**) are mounted by **Catalog Composer** when it starts. Whether each mount is attached is controlled by environment variables that are read **at import time** (when `catalog_composer.py` is loaded). Set or change them **before** launching the process; restarting the process is required after edits.

**Defaults:** if you do **not** set the `MCP_ENABLE_*` variables, all three catalog MCP mounts are **enabled**.

| Variable | Purpose | To **enable** (default if unset) | To **disable** |
|----------|---------|-----------------------------------|------------------|
| **`MCP_ENABLE_SKILL_CATALOG_MCP`** | Mount skill catalog tools (`list_skills`, `add_skill`, …) | `true`, `1`, `yes`, `on`, or unset | `false`, `0`, `no`, `off` |
| **`MCP_ENABLE_AGENT_CATALOG_MCP`** | Mount agent catalog tools | same | same |
| **`MCP_ENABLE_WORKFLOW_CATALOG_MCP`** | Mount workflow catalog tools | same | same |

**Transport (how clients connect to this MCP server):** set **`MCP_MODE`** to **`http`** (default) or **`stdio`**. This selects the wire protocol for the composer process; it is separate from the per-mount enable flags above.

**Example `.env` fragment** (Postgres + all three catalog MCP servers + HTTP):

```bash
MCP_DATABASE_TYPE=postgres
MCP_DATABASE_URL=postgresql://<suername>:=<p w d>@db.example.com:<port>/<db_name>

MCP_MODE=http

# Optional: omit these lines to keep all three mounts enabled (default).
# MCP_ENABLE_SKILL_CATALOG_MCP=true
# MCP_ENABLE_AGENT_CATALOG_MCP=true
# MCP_ENABLE_WORKFLOW_CATALOG_MCP=true
```

**Run Catalog Composer** after exporting the variables or with `.env` present next to the process working directory (dotenv discovery is implemented in `catalog_factory`; align with how you deploy):

```bash
cd modules/mcp_composer && uv run python composers/catalog_composer.py
```

Check logs for a line similar to `Starting Catalog Composer … skill=… agent=… workflow=…`—those booleans reflect whether each catalog MCP mount was enabled at import time.

## What “catalog” means here

MCP Composer uses the word **catalog** in two unrelated ways:

| Meaning | Authoritative store | Typical use |
|--------|---------------------|-------------|
| **Runtime catalog** | Rows in **`catalog_resources`** (plus optional metadata and embeddings tables) | Skills, agents, workflows, prompts—anything stored as a versioned **`kind` + `name` + `version`**. |
| **Backstage / file catalog** | YAML on disk from **`mcp-composer catalog generate-catalog`** | IDP discoverability; **does not** write to **`catalog_resources`**. |

Throughout orchestration and registry documentation, **catalog** means the **runtime** store unless the text explicitly refers to Backstage or `generate-catalog`.

## PostgreSQL schema

After you apply the project DDL, a schema browser should show **three** tables in the database you configured (usually `public`). Their names are fixed by [`scripts/sql/catalog_schema.sql`](../../scripts/sql/catalog_schema.sql) and match what the application expects.

**`catalog_resources`** holds the authoritative document for each version. One row exists per **`(kind, name, version)`**. Important columns include **`payload`** (JSON document for that kind), **`official_meta`**, **`tenant_ids`**, **`is_latest`**, optional **`content`** (for example a large Markdown body that list/get queries omit by default), and timestamps. The **`kind`** column partitions the same physical table for skills, agents, workflows, prompts, and any future kinds without changing the storage pattern.

**`catalog_resource_metadata`** holds at most one **private** JSON document per catalog row, keyed by **`resource_id`** referencing **`catalog_resources.id`**. Rows cascade when the parent resource is deleted. This data is **not** part of the public list/get document for registry consumers; use it for secrets or transport details that must not appear in **`payload`**.

**`catalog_embeddings`** stores an optional vector and model metadata per **`resource_id`**, with pgvector enabled by **`CREATE EXTENSION IF NOT EXISTS vector`** at the top of the DDL script. The shipped **`CatalogPostgresAdapter`** focuses on resources and metadata tables; treat **`catalog_embeddings`** as part of the schema for semantic search when that feature is wired end-to-end.

**`is_latest`:** the DDL enforces that at most one row per **`(kind, name)`** may have **`is_latest = true`**, so clients can resolve “current” without implementing semver range logic themselves.

Apply the script **once**, in file order, against the target database. There is no separate migration runner inside the application beyond executing that SQL.

## Connection, table names, and environment variables

For a procedural checklist (DDL, `psql`, and when to set variables), see **Setup and enabling catalog MCP** above. The subsections here are the compact reference.

The catalog layer does **not** use a dedicated `MCP_CATALOG_DATABASE_URL`. It reuses the same **`MCP_DATABASE_*`** family as the broader composer database configuration. Whatever database you point at must contain the **`catalog_*`** objects after you run **`catalog_schema.sql`**.

**Table names are not configurable** through environment variables: `CatalogPostgresAdapter` uses the literals **`catalog_resources`** and **`catalog_resource_metadata`**. You do **not** need new variables to “register” those names. The only optional exception documented in code is **`CATALOG_RESOURCE_METADATA_JSON_COLUMN`**, which defaults to **`data`** and can be set to a legacy column name such as **`private_meta`** if your database was created from an older DDL variant.

**Factory behavior** ([`catalog_factory.py`](../../modules/mcp_composer/src/mcp_composer/store/catalog_factory.py)) is deterministic:

1. If **`MCP_DATABASE_TYPE`** is **`postgres`** (exact string after trim; **`postgresql`** does **not** match), the factory builds **`CatalogPostgresAdapter`** from **`MCP_DATABASE_URL`** or from host, name, user, password, and optional port.
2. Otherwise, if **`MCP_USE_LOCAL_FILE_STORAGE`** is truthy (`true`, `1`, `yes`, `on`), the factory uses **`CatalogLocalFileAdapter`** rooted at **`MCP_CATALOG_FILE_PATH`** (default relative path **`catalog`**).
3. Otherwise the factory still falls back to **`CatalogLocalFileAdapter`** with that same default root—useful for laptops without Postgres, but **not** a shared production pattern.

**PostgreSQL (shared registry)**

| Variable | Notes |
|----------|--------|
| **`MCP_DATABASE_TYPE`** | Set to **`postgres`**. |
| **`MCP_DATABASE_URL`** | Preferred when set; discrete host fields are ignored for URL-based construction. |
| **`MCP_DATABASE_HOST`**, **`MCP_DATABASE_NAME`**, **`MCP_DATABASE_USER`**, **`MCP_DATABASE_PASSWORD`** | Required together when no URL is provided. |
| **`MCP_DATABASE_PORT`** | Optional; defaults to **5432**. |

**Local files (no SQL tables)**

| Variable | Notes |
|----------|--------|
| **`MCP_USE_LOCAL_FILE_STORAGE`** | Truthy values select file mode when type is not **`postgres`**. |
| **`MCP_CATALOG_FILE_PATH`** | Root directory for catalog files; default **`catalog`**. |

No additional env vars are **required** for a new Postgres database beyond the **`MCP_DATABASE_*`** set above. Start any process that calls **`get_catalog_db()`**, then **`await db.initialize()`** (as Catalog Composer does indirectly through managers), so the pool opens against the database that already has the DDL applied.

## Storage API and managers

All kinds share one abstract port: **`CatalogDatabaseInterface`** in [`catalog_database.py`](../../modules/mcp_composer/src/mcp_composer/store/catalog_database.py). Concrete adapters implement **`initialize`** / **`close`**, upsert and fetch **`catalog_resources`**, optional **`content`** accessors, and private metadata CRUD. Callers work in terms of **`kind`** and row dictionaries; they are not split into separate `get_skill` / `get_agent` methods at the adapter boundary.

Business rules—validation, **`is_latest`** maintenance, version caps—live in **managers** such as **`SkillManager`**, **`AgentManager`**, and **`WorkflowManager`**, which compose the adapter. Operators rarely call the adapter directly; they use MCP tools or HTTP routes that those managers back.

## Resource kinds

The **`kind`** column selects which JSON schema applies to **`payload`**. Common values:

| `kind` | Role |
|--------|------|
| **`skill`** | Agent-facing guidance; payload aligns with [agentskills.io](https://agentskills.io)-style skill documents. |
| **`agent`** | Published agent definitions; may reference skills by name and version in payload (logical reference, not a foreign key). |
| **`workflow`** | Multi-step playbooks; one catalog row per workflow. See [Workflow management](./workflow-management.md). |
| **`prompt`** | Prompt-like rows when your deployment uses them. |

New kinds can appear over time; the **row shape** in **`catalog_resources`** stays the same.

## Changing catalog data

Operators mutate the registry through MCP tools (below), not by hand-editing JSON in the database under normal circumstances.

**Publishing a full document** means calling **`add_*`** with a validated JSON string, or **`publish_*_bundle`** when the same request must include optional **`catalog_resource_metadata`**. Those paths upsert **`(kind, name, version)`** and let the relevant manager reconcile **`is_latest`**.

**Lifecycle-only updates** (for example moving between draft, active, deprecated, or—for skills—**`load-onstartup`**) use **`update_skill_status`**, **`update_agent_status`**, or **`update_workflow_status`** so you do not resend the entire payload.

**Deletion** is always by explicit **`name`** and **`version`** on the corresponding **`delete_*`** tool.

Where HTTP is deployed, skill routes may mirror a subset of these behaviors; the canonical tool-level contract for skills is documented in [Skill management](./skill-management.md).

## MCP surfaces: three catalog servers

Each catalog family is a **FastMCP** sub-application mounted on **`MCPComposer`** with its own **namespace**. Clients therefore often see tool names prefixed with that namespace (for example **`skill-catalog_list_skills`**). Always verify the exact strings your client lists after connecting, because prefixing depends on mount configuration.

| Namespace | Source module | `kind` | Responsibility |
|-----------|---------------|--------|------------------|
| **`skill-catalog`** | [`skill_catalog_mcp.py`](../../modules/mcp_composer/src/mcp_composer/core/tools/catalog/skill_catalog_mcp.py) | **`skill`** | List, get, publish, status, delete, and reference loading for skills; optional **`skill://`** resources are covered in [Skill management](./skill-management.md). |
| **`agent-catalog`** | [`agent_catalog_mcp.py`](../../modules/mcp_composer/src/mcp_composer/core/tools/catalog/agent_catalog_mcp.py) | **`agent`** | Same pattern for agents. |
| **`workflow-catalog`** | [`workflow_catalog_mcp.py`](../../modules/mcp_composer/src/mcp_composer/core/tools/catalog/workflow_catalog_mcp.py) | **`workflow`** | CRUD + one MCP tool per workflow + execution guide. [Workflow management](./workflow-management.md). |

Across the three surfaces, the verbs line up the same way: **list**, **get**, **add** / **publish bundle**, **update status**, **delete**. Skills additionally expose **`load_skill_reference`** for controlled HTTPS fetches of declared reference files.

## Catalog Composer and enabling the MCP surfaces

Step-by-step instructions for environment variables and the **`MCP_ENABLE_*_CATALOG_MCP`** flags are in **Setup and enabling catalog MCP** above. The following paragraphs summarize behavior and runtime details.

**Catalog Composer** ([`catalog_composer.py`](../../modules/mcp_composer/composers/catalog_composer.py)) is the maintained entry process for “registry only”: it mounts all three catalog servers and starts an optional poller for skills in **`load-onstartup`** status.

Run it from the **`mcp_composer`** package directory so imports resolve:

```bash
cd modules/mcp_composer && uv run python composers/catalog_composer.py
```

**`MCP_MODE`** selects **`http`** or **`stdio`** (default **`http`**). See the module docstring for the full env surface, including **`MCP_COMPOSER_TENANT_ID`**, **`MCP_COMPOSER_ALLOWED_TOOLS`**, and **`MCP_COMPOSER_SKILL_REFRESH_INTERVAL_SECS`** for the startup skill poller.

Each catalog mount can be turned off independently. Values are read at **import** time; use case-insensitive **`true` / `1` / `yes` / `on`** to enable and **`false` / `0` / `no` / `off`** to disable. Unset means **enabled**.

| Variable | Effect when disabled |
|----------|----------------------|
| **`MCP_ENABLE_SKILL_CATALOG_MCP`** | **`skill-catalog`** tools are not mounted. |
| **`MCP_ENABLE_AGENT_CATALOG_MCP`** | **`agent-catalog`** tools are not mounted. |
| **`MCP_ENABLE_WORKFLOW_CATALOG_MCP`** | **`workflow-catalog`** tools are not mounted. |

Those flags **do not** disable the **`load-onstartup`** poller; that loop is separate (see startup refresh in [Skill management](./skill-management.md)).

If you embed **`MCPComposer`** in your own service, reproduce **`setup_catalog_mcp`**: call **`composer.mount(get_skill_mcp(), "skill-catalog")`** and the analogous **`get_agent_mcp`** / **`get_workflow_mcp`** mounts, and honor the same enable flags if you copy that helper.

**`MCP_SKILL_CATALOG_LAYERED=true`** changes how **`list_skills`** presents categories for browsing; see instructions in **`skill_catalog_mcp.py`**.

## How operators reach the registry

In production the **database** is the system of record: there is no parallel “catalog filesystem” that replaces **`catalog_resources`** for authoritative skill or agent documents.

Day-to-day access is through:

- **MCP tools** on Catalog Composer (or a custom composer that mounts the same apps).
- **HTTP APIs** where your deployment exposes them (skills are the most common HTTP mirror).
